# Interface locale des actions

Depuis la racine de Work :

```sh
uv run tools/tasks-web/tasks-web.py
```

Le script déclare sa dépendance (`markdown-it-py`, pour le rendu des documents) dans son en-tête PEP 723 : `uv run` l'installe seul, sans environnement à préparer. La page elle-même est en HTML, CSS et JavaScript sans étape de construction ni ressource réseau (ni police web, ni CDN) : la police est celle du système.

Ouvrir ensuite `http://127.0.0.1:8765/` dans le navigateur. Arrêter le serveur avec `Ctrl+C`. Pour choisir un autre port : `uv run tools/tasks-web/tasks-web.py --port 8766`.

Sur macOS, construire l'application locale avec `./tools/tasks-web/build-dock-app.sh`. Le résultat se trouve dans `artifacts/internal/setup/tasks-dock-app/Actions Brain.app` ; on peut l'ajouter au Dock. Un clic sur l'icône démarre le serveur sur le port 8765 s'il est arrêté, attend qu'il réponde, puis ouvre la page dans le navigateur par défaut. Les clics suivants réutilisent le serveur déjà lancé. **Quitter Actions Brain…**, dans le menu ⋯ en bas de la barre latérale, demande une confirmation puis arrête le serveur local ; selon le navigateur, l'onglet se ferme ou affiche un message de fin. Le journal et le PID sont dans `agents/`. L'application contient le chemin de Work au moment de sa construction : après avoir déplacé Work sur une autre machine, reconstruire l'application sur celle-ci. La commande `shortcuts` de macOS ne crée pas de nouveau raccourci en ligne de commande ; cette application AppleScript fournit directement le comportement demandé dans le Dock.

## Disposition

La page occupe exactement la hauteur de la fenêtre, sans défilement de la page : chaque zone (lignes, colonnes du tableau, listes et documents, catalogue et sortie des outils, dépôts et différences Git, panneau de détail) défile séparément. Elle fonctionne de 375 px de large à l'écran large.

- **Barre latérale** (248 px). En haut, le sélecteur de brain (voir « Plusieurs brains »). Puis la navigation : **Aujourd'hui** (nombre d'actions en retard ou du jour), **Actions** (nombre d'actions ouvertes), **Tableau**, **Notes**, **Recherche**. Puis **Projets** : les registres du brain, regroupés par client (le client puis ses missions) ou par dossier (`projects/internal/` devient « Interne »), chacun avec son nombre d'actions ouvertes ; un clic filtre la vue courante (un client filtre toutes ses missions), **Tous les projets** retire le filtre. En pied : **Outils**, **Git** (nombre de changements locaux, une fois la vue ouverte), l'heure de la dernière actualisation et le menu ⋯ : **Actualiser**, **Annuler** (la dernière écriture, avec son libellé), **Raccourcis clavier**, **Quitter Actions Brain…**. La touche `[` ou le bouton en tête de vue masque la barre (choix retenu par le navigateur) ; sous 900 px elle devient un tiroir ouvert par ce bouton, fermé par Échap, la croix ou un clic à côté.
- **En-tête de vue** : titre et compteur, champ de recherche (`/` y place le curseur : il filtre les actions dans Aujourd'hui, Actions et Tableau, cherche dans les documents dans Recherche, filtre les outils dans Outils), **Nouvelle note** et **Nouvelle action** (`n`). Dessous, une ligne de filtres en puces : **Projet** (quand un projet de la barre latérale est choisi, avec une croix pour le retirer), **Responsable** (Tout le monde ou Moi), **Statut** (Ouvertes, Toutes, Terminées et annulées ; vues Actions et Tableau), **Groupe**, **Emplacement** (Partout, Inbox, Hors projets ; vues Notes et Recherche). **Effacer** n'apparaît que lorsqu'un filtre est actif et revient aux actions ouvertes de tous les projets. Dans Actions, **Tout replier** et **Tout déplier** agissent sur les projets.
- **Couleur du brain.** Chaque brain a une couleur d'accent stable, pour savoir toujours dans quel brain on écrit : bleu acier pour `brain`, prune pour `brain-perso`, puis sarcelle, olive, rouille ou ardoise pour les autres, choisie par hachage du nom. Elle ne sert qu'à la marque du brain dans la barre latérale, à l'élément de navigation actif, au bouton principal, à l'anneau de focus, à la ligne choisie et au liseré en haut de la fenêtre.
- **Statuts** : un petit pictogramme de couleur suivi du libellé dans les menus (cercle vide pour À faire, demi-disque pour En cours, pause pour En attente, disque coché pour Terminée, disque barré pour Annulée, avec l'intitulé barré). Une échéance dépassée est en rouge. Priorité : double chevron montant pour Haute, chevron montant pour Moyenne, chevron descendant pour Basse, rien pour Normale.

La vue, les filtres, le texte des recherches et les groupes repliés restent sélectionnés après un rafraîchissement du même onglet (stockage de session du navigateur) ; aucun contenu de tâche n'y est enregistré.

L'interface suit automatiquement le réglage clair ou sombre du système (`prefers-color-scheme`), sans bouton de bascule. Les seuls mouvements (glissement du panneau, fondu des menus) répondent à une action et disparaissent quand le système demande moins d'animations (`prefers-reduced-motion`). Le focus clavier est toujours visible.

## Aujourd'hui

La vue d'ouverture. Elle répartit les actions ouvertes, après les filtres de l'en-tête, en sections (une action n'apparaît qu'une fois, dans la première qui convient) :

1. **En retard** : mes actions dont l'échéance est passée.
2. **Aujourd'hui** : mes actions dues aujourd'hui, ou planifiées (`⏳`) pour aujourd'hui ou avant.
3. **En cours** : mes autres actions en cours.
4. **En attente des autres** : les actions en attente (`[w]`), et celles d'un autre responsable, quelle que soit leur date.
5. **Cette semaine** : mes actions dues ou planifiées dans les 7 jours.

« Mes » actions sont celles dont le responsable contient le nom `owner` de `<brain>/.data/doctor.json` (à défaut `BRAIN_OWNER`) ; sans nom configuré, toutes les actions sont les miennes. Les sections vides sont masquées ; si tout est vide, la vue le dit et propose **Nouvelle action** (ou **Effacer les filtres** quand un filtre est actif). Les données sont celles de `GET /api/actions` (`actions`, `owner`, `registers`, `today`) : le serveur ne calcule rien de plus.

## Actions et panneau de détail

La liste range les actions par projet, puis par groupe (voir « Groupes ») ; chaque en-tête se replie et montre la part d'actions faites (`faites/total`, annulées exclues, quel que soit le filtre Statut), une fine barre de progression et le nombre d'actions en retard ; son **+** (au survol) crée une action dans ce projet et ce groupe. Chaque ligne tient sur une ligne : pictogramme de statut, ID, intitulé (coupé, complet en infobulle et dans le panneau), responsable, échéance relative (« aujourd'hui », « demain », « hier », sinon « lun. 27 oct. »), priorité. Aujourd'hui ajoute la colonne projet. Au survol, au focus ou sur la ligne choisie apparaissent **Ouvrir le détail** et **Supprimer**.

- **Statut en un ou deux clics** : un clic sur le pictogramme ouvre un menu des cinq statuts (chiffres 1 à 5 au clavier). **Échéance** : un clic sur la date ouvre Aujourd'hui, Demain, Lundi prochain, Dans une semaine, une date au choix et **Retirer l'échéance**. Ces écritures renvoient la ligne entière, groupe inchangé, et gardent la position de défilement et la sélection (si l'action quitte la vue, la sélection passe à la ligne suivante).
- **Supprimer** retire l'action sans confirmation (le message propose **Annuler**), avec les mêmes vérifications `version` et `details_version` (les détails sont chargés au besoin) et la même pile d'annulation ; sur un conflit (409), la liste est actualisée et un bandeau demande de vérifier l'action avant de recommencer. Pour garder la trace d'une action abandonnée, préférer le statut **Annulée**.
- **Panneau de détail.** Un clic sur une ligne ou une carte (ou Entrée sur la ligne choisie) ouvre un panneau de 420 px à droite, plein écran sous 700 px. Il remplace l'ancien éditeur, la fiche en lecture et l'aperçu au survol. En tête, l'ID et le projet ; puis l'intitulé complet, modifiable (une seule ligne au registre : Entrée enregistre) ; Statut, Responsable, Échéance, Planifiée pour, Priorité, Groupe ; l'historique ; la création, la dernière mise à jour et la clôture éventuelle ; **Supprimer** en bas. **Enregistrer** (ou ⌘ Entrée) n'est actif que s'il y a un changement ; le panneau reste ouvert et suit la nouvelle version de la ligne. **Fermer** ou Échap le referme (confirmation s'il reste des modifications) et rend le focus à la ligne. Tant qu'il n'est pas modifié, il suit la sélection (`j`, `k`) et les rafraîchissements ; une action disparue le ferme.
- **Création** : **Nouvelle action** ou `n` ouvre le même panneau avec le choix du projet (par défaut le projet filtré), l'intitulé, les champs et le groupe ; Entrée ou **Créer l'action** l'écrit, ferme le panneau et choisit la nouvelle ligne.
- **Historique et notes** : les sous-puces du registre (la `source:` en gris, non supprimable ; `créée` et `mise à jour` sont montrées comme dates sous l'historique). Le bouton **+** ouvre un champ pour ajouter une ou plusieurs notes à la suite (Entrée valide, Échap ferme le champ), chacune écrite immédiatement au registre sous la forme `    - JJ/MM : texte` après les sous-puces existantes ; la corbeille d'une note (avec confirmation) la supprime avec ses sous-détails. Ces écritures vérifient `details_version` et signalent un conflit si le registre a changé.

Quand on change l'état d'une action (panneau, menu de statut ou glisser-déposer), l'écriture la déplace aussi dans la section qui correspond (`Ouvertes`, `Terminées`, `Annulées`), en une seule étape d'annulation ; seule cette action est rangée. Toutes les écritures sur les actions (création, modification, statut, échéance, ajout ou suppression d'historique, suppression) passent par `tools/brain/action.py`, lancé en commande, l'outil que les agents utilisent aussi : il pose `➕` et les sous-puces `créée` et `mise à jour` (date et heure). Une action terminée ou annulée conserve son ID ; la date de clôture est écrite dans sa ligne. Les autres actions mal rangées restent pour `action.py sweep`.

## Tableau

Quatre colonnes, **À faire**, **En cours**, **En attente** et **Terminées récemment** (les 10 dernières clôtures, terminées ou annulées), avec leur nombre ; chaque colonne défile seule et, sur téléphone, elles se succèdent horizontalement. Les cartes sont plates, avec un liseré de 3 px à gauche dans la couleur du statut : pictogramme de statut (même menu que la liste), intitulé sur deux lignes au plus, puis l'ID, la mission et l'échéance ; la corbeille apparaît au survol. On change de colonne par glisser-déposer, vers n'importe quel point d'une colonne. Le filtre Statut « Terminées et annulées » ne laisse que la dernière colonne.

## Groupes (lots)

Un groupe est une étiquette facultative d'action, pas une tâche parente : le registre le note par un tag `#lot/<slug>` en fin d'intitulé (voir `tools/brain/action.md`). Le champ **Groupe** du panneau est une liste : **Aucun groupe**, les groupes déjà utilisés dans le projet choisi (libellés triés ; la liste suit le changement de projet), puis **Nouveau groupe…**, qui affiche un champ texte (focus automatique) pour un libellé libre (« Atelier ingestion »), converti en slug (minuscules, accents retirés, tirets, 40 caractères au plus) ; l'aide sous le champ montre le slug qui sera enregistré. Le groupe de l'action, ou celui pré-rempli par un **+**, est ajouté comme option choisie s'il manque à la liste ; si l'on change de projet en création et que le groupe choisi n'y existe pas, il revient en « Nouveau groupe… » avec son libellé.

Chaque groupe a une pastille de couleur stable, dérivée de son slug (8 teintes `--grp-0…7`, variantes sombres comprises), sur les en-têtes de groupe seulement. Dans **Actions**, chaque projet montre ses groupes (triés par libellé), puis ses actions sans groupe sous « Sans groupe » quand le projet a aussi des groupes ; les lignes d'un groupe sont légèrement décalées. Dans le **Tableau**, dès qu'une colonne contient une action groupée, ses cartes sont rangées sous un intitulé par couple projet et groupe (pastille, libellé, mission en discret, nombre de cartes), triés par projet puis libellé, les cartes sans groupe à la fin sous « Sans groupe » ; l'ordre des cartes dans un groupe reste celui de la colonne et « Terminées récemment » garde ses 10 cartes, choisies avant le regroupement ; les cartes groupées montrent le responsable à la place de la mission. Un groupe replié l'est dans la liste et dans toutes les colonnes (clé `registre|slug` ; `registre|` pour « Sans groupe » d'un projet, `p:registre` pour un projet, `|` pour « Sans groupe » d'une colonne), gardé avec la vue dans le stockage de session (aucun intitulé). Le **+** d'un groupe crée une action dans le même projet et le même groupe, dans l'état de la colonne (À faire pour « Terminées récemment »), sans rien déplacer.

La puce **Groupe** propose **Tous**, **Sans groupe**, puis les groupes du registre : un `<optgroup>` par projet quand aucun registre précis n'est filtré (l'infobulle donne « Projet : Libellé »), les seuls groupes du projet filtré sinon ; elle est gardée avec les autres filtres, remise à zéro par **Effacer** et revient à « Tous » si le groupe enregistré n'existe plus. La recherche d'actions porte aussi sur le libellé et le slug du groupe. API : chaque action de `GET /api/actions` porte `group` (slug ou chaîne vide ; `title` et `raw_title` sont sans le tag) et chaque registre de `registers` porte `groups` (slugs utilisés, triés) ; `POST` et `PATCH /api/actions` acceptent un champ `group` facultatif (absent : inchangé en modification, aucun à la création ; `""` : retire le groupe ; slug invalide : 400, comme un intitulé qui se termine par un tag `#lot/…`). Un changement de statut ou d'échéance ne l'envoie pas, et l'annulation restaure les octets du registre comme pour toute écriture.

## Annuler et messages

Chaque écriture faite depuis l'interface (création, modification, statut, échéance, ajout ou suppression de note, suppression d'action, création ou modification de note) affiche un court message en bas au centre, au passé (« Action créée », « Statut mis à jour », « Action supprimée »…), avec un bouton **Annuler** tant que l'annulation est possible. **Annuler** du menu ⋯ et ⌘ Z (Ctrl+Z sur Windows et Linux, hors d'un champ de saisie) annulent la dernière écriture, puis les précédentes à chaque fois (20 au plus) ; la pile est en mémoire, perdue à la fermeture du serveur, et l'annulation est refusée si le fichier a changé entre-temps.

## Raccourcis clavier

Ils ne s'appliquent pas pendant la saisie dans un champ ; `?` affiche leur aide, et les infobulles les rappellent.

| Touche | Effet |
|---|---|
| `/` | Rechercher ou filtrer dans la vue |
| `n` | Nouvelle action |
| `1` à `5` | Aujourd'hui, Actions, Tableau, Notes, Recherche |
| `j` `k`, `↓` `↑` | Action suivante ou précédente (Aujourd'hui, Actions, Tableau) |
| Entrée | Ouvrir le détail de l'action choisie |
| `s` | Menu de statut de l'action choisie |
| `d` | Échéance de l'action choisie |
| Échap | Fermer le menu, le tiroir ou le panneau |
| ⌘ Entrée | Enregistrer le panneau ou la note en cours de modification |
| ⌘ Z | Annuler la dernière écriture |
| `[` | Afficher ou masquer la barre latérale |
| `?` | Aide des raccourcis |

Dans une liste, seule la ligne choisie (à défaut la première) est dans l'ordre de tabulation : Tab parcourt ses boutons, `j` et `k` passent aux autres.

## Plusieurs brains

Un même Work peut contenir plusieurs brains : les dossiers de la racine nommés `brain` ou `brain-<nom>` qui portent un `AGENTS.md` et un dossier `.data/` (la règle de `tools/brain/brain-state.py` et de `tools/machine/work_config.py` ; `brain` d'abord, les autres par ordre alphabétique). Le sélecteur en haut de la barre latérale change de brain sans redémarrer le serveur : un bouton qui affiche le nom court du brain en grand et son `scope` en dessous (précédés du mot « Brain » pour lecteur d'écran), et ouvre une liste où chaque brain apparaît avec sa couleur, son nom et son `scope` (le nom du dossier et le `description` en infobulle), lus dans `<brain>/.data/brain.json` quand il existe. La page affiche un nom court, pas le nom du dossier : `brain-<suffixe>` devient le suffixe avec une majuscule initiale (`brain-perso` → « Perso », `brain-acme-corp` → « Acme-corp »), `brain` devient « Brain » ; le nom du dossier reste la valeur technique (`?brain=`, `localStorage`, API) et le libellé est calculé par le serveur (champ `label`). Au clavier : Entrée, Espace ou les flèches ouvrent la liste, les flèches, Début et Fin se déplacent, une lettre saute au brain suivant qui commence par elle, Entrée ou Espace choisit, Échap referme. Avec un seul brain, son nom reste un simple texte. La liste est relue à l'ouverture du sélecteur et par **Actualiser** : un brain ajouté en cours de route apparaît, et un brain disparu ramène la page au brain par défaut. Le brain courant vient de `?brain=<nom>` dans l'adresse, puis de la mémoire du navigateur (`localStorage`), sinon du brain par défaut du serveur ; l'adresse est tenue à jour (`history.replaceState`), ce qui permet de garder un onglet par brain. Au changement, la page remet à zéro ce qui appartient à l'ancien brain (filtre de projet, groupe, groupes repliés, sélection, panneau de détail, document ouvert, sélection et détail Git, sortie des outils, pile **Annuler**) puis recharge les vues avec les fonctions de rafraîchissement habituelles ; le texte tapé dans les champs de recherche et les filtres Responsable et Statut restent. Le changement est refusé tant qu'une écriture ou un outil est en cours, et une action ou une note modifiée et non enregistrée demande confirmation. Une réponse de lecture qui arrive après le changement est ignorée.

Côté serveur, `--brain` désigne seulement le brain par défaut (sans option : `Work/brain`) et `WORK_DIR` une autre racine de Work. S'il ne fait pas partie des brains découverts, il est proposé quand même, seul ou en tête de liste. Chaque brain a son propre `Store`, créé à la première demande et gardé : sa pile d'annulation et son cache de documents ne se mélangent pas à ceux des autres. Toutes les routes `/api/…` acceptent un paramètre `brain=<nom>` facultatif ; absent, c'est le brain par défaut et les réponses sont celles d'avant. Le nom doit être exactement celui d'un brain découvert à l'instant de la requête : un chemin, un nom inconnu, vide ou répété donne une erreur 400 (`{"error": "Brain inconnu."}`), et un brain sans dossier `projects/` une 404. L'outil lancé depuis **Outils** reçoit le brain choisi (`BRAIN_DIR`), la vue **Git** montre Work et le dossier du brain choisi, les écritures (actions, notes, historique, suppression, annulation) n'atteignent que lui. Route : `GET /api/brains` → `{"brains": [{"name", "label", "scope", "description", "default"}], "default": "<nom>"}` (`label` : nom court affiché, `Perso` pour `brain-perso` ; `scope` et `description` valent `""` sans `brain.json` ; la liste est relue à chaque appel ; ni jeton ni écriture).

## Notes et Recherche

**Notes** liste les notes du brain (celles de `GET /api/notes` : `<projet>/notes/*.md` et l'Inbox), les plus récentes d'abord, avec le projet, la date et un extrait ; **Recherche** cherche dans tous les documents Markdown du brain. Les deux vues partagent le lecteur à droite (sous la liste sur écran étroit) et les filtres : le projet de la barre latérale (un client garde les documents de toutes ses missions) et la puce **Emplacement** (**Inbox** pour le dossier `inbox/`, **Hors projets** pour les documents qui ne sont sous aucun dossier de projet ; choisir l'un retire le projet de la barre latérale, et inversement).

Périmètre de la recherche : tous les `*.md` sous le brain, sauf tout chemin dont un composant commence par `.` (`.git`, `.data`, `.vscode`, `.obsidian`, `.trash`…), les liens symboliques, ce qui sort du brain et les fichiers de plus de 1 Mo. Le catalogue analysé est mis en cache par fichier (chemin, date de modification, taille) : seuls les fichiers modifiés sont relus.

Dans **Recherche**, le champ de l'en-tête (pris au focus en entrant dans la vue, lancé après 200 ms d'inactivité ou tout de suite avec Entrée) remplace la liste des documents **Modifiés récemment** par les résultats : titre (premier titre `# `, sinon le nom du fichier) avec les termes surlignés, projet, chemin abrégé (sans `projects/` ni `clients/`) et jusqu'à 2 extraits d'environ 160 caractères ; le nombre de résultats s'affiche dans l'en-tête. Règles de recherche : les accents, la casse et les espaces multiples sont ignorés (`réunion` trouve `REUNION`) ; les mots séparés par des espaces doivent tous apparaître (ET) dans le titre, le chemin ou le contenu ; `"entre guillemets"` cherche une expression exacte ; 10 termes au plus, 60 caractères par terme et 300 caractères au total (au-delà, erreur 400), les termes d'un seul caractère sont ignorés. Le tri pondère le titre (×10), le chemin (×5), les lignes de titre Markdown (×3) et les occurrences dans le corps (plafonnées), avec un léger avantage aux fichiers récents ; les 50 meilleurs résultats sont renvoyés (avec un client choisi dans la barre latérale, le tri se fait sur ces 50).

Lecteur : le document est rendu en HTML par le serveur (`markdown-it-py`, CommonMark avec tableaux et texte barré), en lignes de 72 caractères au plus. Le HTML brut des documents n'est jamais interprété : il s'affiche comme du texte. Les images ne sont pas chargées (leur texte alternatif s'affiche). Les titres reçoivent un identifiant (préfixe `h-`) pour les ancres. Les liens relatifs vers un autre `.md` du brain ouvrent ce document dans le même lecteur, avec un bouton **Retour** ; les liens `http(s)` et `mailto` s'ouvrent dans un nouvel onglet (`noopener noreferrer`) ; les autres liens (fichiers non Markdown, documents hors du brain ou absents, schémas `javascript:`, `data:`, `file:`…) s'affichent comme du texte avec l'infobulle « Fichier non affiché ici ». Un document ouvert depuis une recherche a ses termes surlignés (500 surlignages au plus) et défile jusqu'au premier. Pour une note de projet ou de l'Inbox, **Modifier** ouvre le Markdown brut ; **Enregistrer** (ou ⌘ Entrée) remplace le fichier si sa version n'a pas changé sur le disque (sinon message de conflit), **Annuler** abandonne, avec confirmation s'il reste des modifications non enregistrées, et le rendu est rafraîchi après l'enregistrement. Les autres documents sont en lecture seule.

**Nouvelle note** demande un titre, un projet (par défaut le projet choisi dans la barre latérale, sinon **Inbox (à trier)**) et un contenu ; après la création, la page passe à la vue **Notes** et affiche la note. Un projet est un dossier contenant `state/actions.md` ; la note vit dans `<projet>/notes/AAAA-MM-JJ-<slug>.md`, fichier plat dont le dossier `notes/` est créé au besoin. La cible **Inbox (à trier)**, proposée en premier, écrit dans `inbox/AAAA-MM-JJ-<slug>.md` à la racine du brain (dossier créé au besoin), pour les notes brutes qu'un agent triera plus tard ; son en-tête est `> Note du JJ/MM/AAAA · à trier`, sans lien de projet. Les notes de l'Inbox apparaissent avec le projet « Inbox » et sont modifiables comme les notes de projet (le `README.md` du dossier n'est jamais listé ni modifiable). Le fichier ne remplace jamais un fichier existant (suffixe `-2`, `-3`… en cas de collision) et commence par `# Titre`, une ligne `> Note du JJ/MM/AAAA · projet : [libellé](lien relatif)` vers la fiche du projet (à défaut vers son registre) et le contenu. Le slug est en ASCII minuscule, 60 caractères au plus ; le titre fait 1 à 150 caractères sur une ligne, le contenu 100 Ko au plus. Les écritures sont protégées comme celles des actions (hôte, origine, jeton, JSON, verrou d'écriture) et passent par la même pile d'annulation : annuler une création supprime la note (et le dossier `notes/` ou `inbox/` s'il a été créé par cette écriture et reste vide), annuler une modification restaure les octets exacts ; l'annulation est refusée si le fichier a changé entre-temps. Après une annulation, les vues relisent la liste ou relancent la recherche et réaffichent le document (« Ce document n'existe plus » s'il a disparu). Routes : `GET /api/search?q=&project=` (`project` : chemin d'un registre, `inbox`, `none` ou vide ; réponse `query`, `terms`, `results` [`id`, `title`, `project`, `register`, `snippets` [`text`, `ranges`], `score`], `total`, `truncated`), `GET /api/docs/recent?project=`, `GET /api/docs/render?id=` (`id` exactement égal à un identifiant du catalogue, sinon 404 ; réponse `id`, `title`, `project`, `register`, `html`, `note`, `version`), `GET /api/notes`, `GET /api/notes/content?id=`, `POST /api/notes` (`title`, `register`, `content` ; `register` est obligatoire : chemin d'un registre de projet, ou `inbox` pour l'Inbox), `PATCH /api/notes` (`id`, `version`, `content` ; 409 si la version est périmée).

## Outils

La vue **Outils** liste, par groupe repliable, les commandes existantes (lecture, prévisualisation, et une écriture confirmée) : contrôles du brain et des liens, vérification des dépôts, ainsi que deux outils du groupe **Actions** : **Actions à archiver (aperçu)** (`brain/action.py`, ne modifie rien) et **Archiver les actions** (`brain/action.py --write`), qui déplace les actions closes depuis plus de 30 jours dans `state/actions-archive-AAAA.md`. Chaque ligne donne le nom, une description d'une ligne (complète en infobulle avec la commande) et **Lancer**. Un outil qui écrit des fichiers du brain porte la marque « modifie le brain », demande une confirmation avant de s'exécuter et rafraîchit les listes ensuite ; ses écritures ne passent pas par la pile d'annulation de l'interface (on les rattrape avec Git). La sortie s'affiche dans un panneau sous la liste, avec la commande lancée, sans être enregistrée par l'interface. Les commandes autorisées et leurs arguments sont fixés côté serveur ; aucun champ ne permet d'exécuter une commande libre. Le clonage de dépôts reste dans son workflow dédié.

Si **Nouvelles transcriptions** affiche « Accès refusé », son dossier d'entrée configuré dans le brain n'est pas lisible par le processus qui lance Actions Brain. Vérifier les autorisations macOS et la disponibilité OneDrive, puis relancer la commande ; l'outil ne présente pas une liste incomplète comme si elle était exhaustive.

## Git

La vue **Git** affiche, en lecture seule, les changements locaux des deux dépôts Work et brain (le dossier du brain choisi), l'un sous l'autre à gauche : branche, avance/retard (`↑` `↓`) par rapport à la dernière synchro locale de la branche distante, fichiers indexés, modifiés et non suivis avec leurs compteurs `+N −M`, et les 2 derniers commits (ceux qui ne sont pas encore poussés sont marqués). Un clic sur un fichier ou un commit affiche son diff à droite (dessous sur écran étroit) ; **Actualiser** relit aussi cette vue. Le serveur n'exécute que des commandes Git de lecture à arguments fixes (`status`, `diff`, `log`, `show`, `rev-list`), sans shell, avec un délai de 10 secondes, sans `GIT_TERMINAL_PROMPT` ni verrou optionnel, et ne contacte jamais le réseau (aucun `fetch`, `pull`, `push` ni `ls-remote` : le retard affiché n'est donc exact qu'après une synchro faite ailleurs). Le chemin demandé doit figurer dans l'état Git courant et le commit parmi les 2 listés, sinon la réponse est 404 ; un fichier indexé et modifié apparaît dans les deux groupes, et pour un fichier seulement indexé le diff indexé est servi. Les sorties sont tronquées à 300 Ko. Les fichiers sensibles (`.env*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `id_ed25519*`, `*.kdbx`, `credentials*`, `*secret*`, `*.token`) sont listés mais leur contenu n'est jamais affiché, ni dans le diff ni dans le détail d'un commit. Aucune action de commit, d'indexation ou de push n'est possible depuis l'interface. Routes : `GET /api/git`, `GET /api/git/diff?repo=&path=&staged=0|1`, `GET /api/git/commit?repo=&hash=`.

## Données et sécurité

Les fichiers `projects/**/state/actions.md` du brain choisi sont la seule source de vérité. Le navigateur lit leur état à l'ouverture et avec **Actualiser** ; il ne stocke pas de copie des tâches. Les écritures passent par un serveur lié à `127.0.0.1`, avec vérification de l'origine et de la version de la ligne pour signaler les modifications concurrentes. Aucune donnée n'est envoyée à un hébergement ou à un service externe. Les IDs sont attribués d'après le préfixe existant et le plus grand numéro du projet ; un registre sans préfixe établi doit d'abord être configuré selon les conventions du brain.

La page `brain/tasks.md` fournit les mêmes vues dans Obsidian, grâce aux plugins Tasks, Meta Bind et Templater (réglages à faire une fois par machine : `kit/obsidian/README.md`). Les deux interfaces utilisent les mêmes registres ; aucune synchronisation supplémentaire n'est nécessaire.
