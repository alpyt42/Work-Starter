# Local actions interface

From the root of Work:

```sh
uv run tools/tasks-web/tasks-web.py
```

The script declares its dependency (`markdown-it-py`, to render documents) in its PEP 723 header: `uv run` installs it on its own, with no environment to prepare. The page itself is plain HTML, CSS and JavaScript with no build step and no network resource (no web font, no CDN): the font is the system one.

Then open `http://127.0.0.1:8765/` in the browser. Stop the server with `Ctrl+C`. To choose another port: `uv run tools/tasks-web/tasks-web.py --port 8766`.

On macOS, build the local app with `./tools/tasks-web/build-dock-app.sh`. The result is in `artifacts/internal/setup/tasks-dock-app/Actions Brain.app`; it can be added to the Dock. A click on the icon starts the server on port 8765 if it is stopped, waits for it to answer, then opens the page in the default browser. Later clicks reuse the server already running. **Quit Actions Brain…**, in the ⋯ menu at the bottom of the sidebar, asks for confirmation then stops the local server; depending on the browser, the tab closes or shows an end message. The log and the PID are in `agents/`. The app contains the path of Work at the time it was built: after moving Work to another machine, rebuild the app on that machine. The macOS `shortcuts` command cannot create a new shortcut from the command line; this AppleScript app directly provides the requested behavior in the Dock.

## Layout

The page takes exactly the height of the window, with no page scrolling: each zone (rows, board columns, the timeline frieze, lists and documents, tools catalog and output, Git repositories and diffs, detail panel) scrolls separately. It works from 375 px wide up to wide screens.

- **Sidebar** (248 px). At the top, the brain selector (see "Several brains"). Then the navigation: **Today** (number of overdue or due-today actions), **Actions** (number of open actions), **Board**, **Timeline**, **Notes**, **Search**. Then **Projects**: the brain's registers, grouped by client (the client, then its missions) or by folder (`projects/internal/` becomes "Internal"), each with its number of open actions; a click filters the current view (a client filters all its missions), **All projects** removes the filter. At the bottom: **Tools**, **Git** (number of local changes, once the view has been opened), the time of the last refresh and the ⋯ menu: **Refresh**, **Undo** (the last write, with its label), **Keyboard shortcuts**, **Quit Actions Brain…**. The `[` key or the button at the head of the view hides the sidebar (the choice is remembered by the browser); below 900 px it becomes a drawer opened by that button and closed by Esc, the cross or a click outside it.
- **View header**: title and counter, search field (`/` puts the cursor in it: it filters actions in Today, Actions and Board, searches the documents in Search, filters the tools in Tools), **New note** and **New action** (`n`). Below, a row of filter chips: **Project** (when a sidebar project is chosen, with a cross to remove it), **Owner** (Everyone or Me), **Status** (Open, All, Done and cancelled; Actions and Board views), **Group**, **Location** (Everywhere, Inbox, Outside projects; Notes and Search views). **Clear** appears only when a filter is active and goes back to the open actions of all projects. In Actions, **Collapse all** and **Expand all** act on projects.
- **Brain color.** Each brain has a stable accent color, so you always know which brain you are writing to: steel blue for `brain`, plum for `brain-perso`, then teal, olive, rust or slate for the others, chosen by hashing the name. It is used only for the brain mark in the sidebar, the active navigation item, the primary button, the focus ring, the selected row, the Timeline's mark for today and the strip at the top of the window.
- **Statuses**: a small colored pictogram followed by the label in menus (empty circle for To do, half-disc for In progress, pause for Waiting, checked disc for Done, crossed-out disc for Cancelled, with the title struck through). An overdue due date is red. Priority: double up chevron for High, up chevron for Medium, down chevron for Low, nothing for Normal.

The view, the filters, the search text and the collapsed groups are kept after a refresh of the same tab (browser session storage); no task content is stored there.

The interface automatically follows the system light or dark setting (`prefers-color-scheme`), with no toggle button. The only movements (panel sliding in, menu fade) respond to an action and disappear when the system asks for less animation (`prefers-reduced-motion`). Keyboard focus is always visible.

## Today

The opening view. It splits the open actions, after the header filters, into sections (an action appears only once, in the first one that fits):

1. **Overdue**: my actions whose due date has passed.
2. **Today**: my actions due today, or scheduled (`⏳`) for today or earlier.
3. **In progress**: my other actions in progress.
4. **Waiting on others**: waiting actions (`[w]`), and those of another owner, whatever their date.
5. **This week**: my actions due or scheduled within the next 7 days.

"My" actions are those whose owner contains the `owner` name from `<brain>/.data/doctor.json` (otherwise `BRAIN_OWNER`); with no name configured, all actions are mine. Empty sections are hidden; if everything is empty, the view says so and offers **New action** (or **Clear filters** when a filter is active). The data is that of `GET /api/actions` (`actions`, `owner`, `registers`, `today`): the server computes nothing more.

## Actions and detail panel

The list arranges actions by project, then by group (see "Groups"); each header collapses and shows the share of actions done (`done/total`, cancelled excluded, whatever the Status filter), a thin progress bar and the number of overdue actions; its **+** (on hover) creates an action in that project and group. Each row fits on one line: status pictogram, ID, title (truncated, complete in the tooltip and in the panel), owner, relative due date ("today", "tomorrow", "yesterday", otherwise "Mon, Oct 27", in the browser locale), priority. Today adds the project column. On hover, on focus or on the selected row, **Open the details** and **Delete** appear.

- **Status in one or two clicks**: a click on the pictogram opens a menu of the five statuses (To do, In progress, Waiting, Done, Cancelled; digits 1 to 5 on the keyboard). **Due date**: a click on the date opens Today, Tomorrow, Next Monday, In a week, a chosen date and **Remove the due date**. These writes send back the whole line, group unchanged, and keep the scroll position and the selection (if the action leaves the view, the selection moves to the next row).
- **Delete** removes the action without confirmation (the message offers **Undo**), with the same `version` and `details_version` checks (the details are loaded when needed) and the same undo stack; on a conflict (409), the list is refreshed and a banner asks you to check the action before trying again. To keep a trace of an abandoned action, prefer the **Cancelled** status.
- **Detail panel.** A click on a row or a card (or Enter on the selected row) opens a 420 px panel on the right, full screen below 700 px. It replaces the former editor, the read-only sheet and the hover preview. At the top, the ID and the project; then the full title, editable (a single line in the register: Enter saves); Status, Owner, Due date, Scheduled for, Priority, Group; "History and notes"; the creation, the last update and the closing if any (Created, Updated, Closed); **Delete** at the bottom. **Save** (or ⌘ Enter) is enabled only when something has changed; the panel stays open and follows the new version of the line. **Close** or Esc closes it (with a confirmation if changes remain) and gives the focus back to the row. As long as it is unmodified, it follows the selection (`j`, `k`) and the refreshes; an action that has disappeared closes it.
- **Creation**: **New action** or `n` opens the same panel with the choice of project (by default the filtered project), the title, the fields and the group; Enter or **Create action** writes it, closes the panel and selects the new row.
- **History and notes**: the register's sub-bullets (the `source:` in gray, not deletable; `created:` and `updated:` are shown as dates under the history). The **+** button opens a field to add one or more notes in a row (Enter adds the note, Esc closes the field), each written immediately to the register as `    - DD/MM: text` after the existing sub-bullets; the trash can of a note (with confirmation) deletes it along with its sub-details. These writes check `details_version` and report a conflict if the register has changed.

When you change the status of an action (panel, status menu or drag and drop), the write also moves it to the matching section (`Open`, `Done`, `Cancelled`), in a single undo step; only that action is filed. All writes on actions (creation, edit, status, due date, adding or deleting history, deletion) go through `tools/brain/action.py`, run as a command, the tool the agents use too: it sets `➕` and the `created:` and `updated:` sub-bullets (date and time). A done or cancelled action keeps its ID; the closing date is written in its line. The other misfiled actions are left for `action.py sweep`.

## Board

Four columns, **To do**, **In progress**, **Waiting** and **Recently done** (the last 10 closures, done or cancelled), with their counts; each column scrolls on its own and, on a phone, they follow one another horizontally. The cards are flat, with a 3 px strip on the left in the status color: status pictogram (same menu as the list), title on two lines at most, then the ID, the mission and the due date; the trash can appears on hover. You change column by drag and drop, to any point of a column. The Status filter "Done and cancelled" leaves only the last column.

## Timeline

The actions that have a deadline, on a chronological frieze, with the ones that have none in a tray under it, so the view both shows what is due and lets you plan what is not. It follows the chosen brain and the header filters that make sense there (search text, **Owner**, **Group**, the sidebar project); the **Status** chip is not offered, its job is done by the **Show done** switch. The page is `GET /api/actions` only (`due`, `scheduled`, `done`, `state`, `owner`, `project`, `group`, and `due_note`, see below): the server computes nothing more. `static/timeline-view.js` is the logic (range, ISO weeks, weekends, the fit-to-width scale and the day under a pointer, placement, overdue, lanes and stacking, summary counts, tray, keyboard neighbours; no DOM, no clock), which the tests also run under node. Dates are formatted like everywhere else in the app, with the browser's locale.

- **Fits the width.** One column per day, from Monday of last week: **2 weeks**, **6 weeks** (the default) or **Quarter** (13 weeks), so a range is always whole weeks, drawn to fill the page with no sideways scroll; weekends are three quarters as wide, tinted and hatched. A range scrolls sideways only when its days would get narrower than the minimum (30, 12 and 6 px per weekday): then the **Today** button and the week arrows scroll it (the arrows only show in that case), and a plain wheel scrolls sideways when that is the only way the frieze can move (Shift+wheel and a trackpad always do). A Quarter has week ticks instead of day numbers (the toolbar says so), and a chip then carries its date. The header has the months, the ISO week numbers with the date of the week's first day (`W44 26 Oct`), and the weekday and day number. Today is a tinted column with a line, and an accent-colored day number.
- **Overdue first.** The zone at the left edge, next to the project labels, is sticky: always visible, tinted with the danger colors, with the count and the date it stops at. It holds the unfinished actions due before the range, per project, each with its date; with none, it shrinks to a mark and gives its room to the days. Overdue actions inside the range are red chips on their day. The **N overdue** pill in the toolbar focuses the first one.
- **Summary strip.** Under the toolbar: **Overdue**, **This week** (today to Sunday), **Next 2 weeks** (the two weeks after), **No deadline** and **Vague**, with the count of open actions each. The first three spotlight those actions (the other chips dim; a second click clears it); the last two open the tray, on its search field or on the vague deadlines. A count of 0 is greyed out.
- **Lanes.** One lane per project that has an open action (in the order of the registers), dated or not. The label has the client and the mission, and **N undated**, which opens the tray on that project; **+** on hover adds an action to the project. Chips on nearby days stack in the lane, so none hides another.
- **Chips.** A chip is an action with a plain due date (`📅`): status pictogram, ID, the initials of the owner when it is not the brain owner, and the title on up to two lines (complete in the tooltip). Its left edge is the due day (a chip that would leave the range ends on its day instead), its strip is the status color, and its thin top line the project's color. A scheduled date (`⏳`) before the due date is a hollow dashed marker on its day, joined to the chip; otherwise the chip carries a small hourglass. Done actions are hidden until **Show done**: they then sit at their done date (`✅`, else their due date), faded. Cancelled actions are never shown, and neither is a scheduled date alone (it is no deadline).
- **No deadline tray.** Under the frieze, collapsible (the choice is kept; it starts closed on a narrow page), searchable (words of the ID, title, owner, project or wording), grouped by project. **Vague deadlines** come first: an action whose deadline is a wording, not a date, which is the `due:` sub-bullet of an action with no `📅` date (`- due: week of 05/10`; `—` means none), given by `GET /api/actions` as `due_note` (empty otherwise; a `📅` date is authoritative). The cards show it in italics.
- **Planning by dragging.** Drag a tray card, or a chip, onto a day: its due date is set or moved. Drag a chip back onto the tray: its date is removed. The write is the one of the detail panel's date field (the same `PATCH /api/actions/<ID>`, through `tools/brain/action.py`), and the message offers **Undo**. Clicking an empty day of a project opens the new-action panel on that project, due that day. Without a mouse: `d` on a chip or a tray card (or the calendar button of a card) opens the date menu, and **Alt+← →** on a chip moves its deadline by a day (**Alt+Shift+← →**: a week), one move at a time.
- **Keyboard, detail panel, assistive tools.** Clicking a chip or a card, or Enter on it, opens the detail panel as in the list and the board; `j`/`k`, `s` and `d` work as there. The chips are one Tab stop; ← → walk a project by date (then by ID), ↑ ↓ change project (skipping the ones without a chip), on the closest date, Home and End go to the ends of the project, and an open, unmodified panel follows. In the tray ↑ ↓ Home End walk the cards. Each chip is a button named in full (ID, title, status, due date and days overdue, scheduled date, project, owner), each project is a pair of lists (overdue, planned), and the headers are decorative since the names carry the dates.
- **Narrow screens.** Under 700 px of page width the frieze becomes an agenda: the overdue actions, then one row per day grouped by week, weekends shaded, today marked, and the same chips (with their project); the strip scrolls sideways and the tray, closed by default, stays under it. The range, the **Show done** switch and the tray's state are kept with the other filters (browser session storage, no task content), and the scroll position survives a refresh.

## Groups

A group is an optional label on an action, not a parent task: the register notes it with a `#group/<slug>` tag at the end of the title (CLI `--group`, see `tools/brain/action.md`). The **Group** field of the panel is a list: **No group**, the groups already used in the chosen project (sorted labels; the list follows the change of project), then **New group…**, which shows a text field (focused automatically) for a free label ("Ingestion workshop"), converted to a slug (lowercase, accents removed, hyphens, 40 characters at most); the help under the field shows the slug that will be saved. The action's group, or the one pre-filled by a **+**, is added as the selected option if it is missing from the list; if you change project during creation and the chosen group does not exist there, it goes back to "New group…" with its label.

Each group has a stable color dot, derived from its slug (8 hues `--grp-0…7`, dark variants included), on group headers only. In **Actions**, each project shows its groups (sorted by label), then its actions without a group under "No group" when the project also has groups; the rows of a group are slightly indented. In the **Board**, as soon as a column contains a grouped action, its cards are arranged under one heading per project and group pair (dot, label, mission in a muted style, number of cards), sorted by project then label, the cards without a group at the end under "No group"; the order of the cards within a group stays that of the column and "Recently done" keeps its 10 cards, chosen before the grouping; grouped cards show the owner in place of the mission. A collapsed group is collapsed in the list and in all columns (key `register|slug`; `register|` for the "No group" of a project, `p:register` for a project, `|` for the "No group" of a column), kept with the view in session storage (no label). The **+** of a group creates an action in the same project and the same group, with the status of the column (To do for "Recently done"), without moving anything.

The **Group** chip offers **All**, **No group**, then the groups of the registers: one `<optgroup>` per project when no specific register is filtered (the tooltip reads "Project: Label"), only the groups of the filtered project otherwise; it is kept with the other filters, reset by **Clear** and goes back to "All" if the saved group no longer exists. The action search also covers the label and the slug of the group. API: each action of `GET /api/actions` carries `group` (slug or empty string; `title` and `raw_title` are without the tag) and each register of `registers` carries `groups` (slugs in use, sorted); `POST` and `PATCH /api/actions` accept an optional `group` field (absent: unchanged on edit, none on creation; `""`: removes the group; invalid slug: 400, like a title that ends with a `#group/…` tag). A status or due date change does not send it, and the undo restores the register's bytes as for any write.

## Undo and messages

Every write made from the interface (creation, edit, status, due date, adding or deleting a note, deleting an action, creating or editing a note) shows a short message at the bottom center, in the past tense ("Action <ID> created", "Status updated", "Action deleted"…), with an **Undo** button as long as undoing is possible. **Undo** in the ⋯ menu (shown as "Undo: <label>", or "Nothing to undo") and ⌘ Z (Ctrl+Z on Windows and Linux, outside an input field) undo the last write, then the previous ones each time (20 at most); the stack is in memory, lost when the server stops, and the undo is refused if the file has changed in the meantime.

## Several brains

A single Work can hold several brains: the folders at the root named `brain` or `brain-<name>` that carry an `AGENTS.md` and a `.data/` folder (the rule of `tools/machine/work_config.py`, shared by the other tools; the default brain first, the others in alphabetical order). The selector at the top of the sidebar switches brain without restarting the server: a button that shows the brain's short name in large type (preceded by the word "Brain" for screen readers), and opens a list where each brain appears with its color and its name; the tooltip of an entry (and of the button) gives the folder name with the `scope`, then the `description`, read from `<brain>/.data/brain.json` when it exists. The page shows a short name, not the folder name: `brain-<suffix>` becomes the suffix with an initial capital (`brain-initech` → "Initech", `brain-acme-corp` → "Acme-corp"), `brain` becomes "Brain"; the folder name remains the technical value (`?brain=`, `localStorage`, API) and the label is computed by the server (`label` field). On the keyboard: Enter, Space or the arrows open the list, the arrows, Home and End move, a letter jumps to the next brain that starts with it, Enter or Space chooses, Esc closes. With a single brain, its name stays plain text. The list is re-read when the selector opens and by **Refresh**: a brain added along the way appears, and a vanished brain brings the page back to the default brain. The current brain comes from `?brain=<name>` in the address, then from the browser's memory (`localStorage`), otherwise from the server's default brain (`--brain`, else the default brain of the Work: `"defaultBrain"` in `work-config.local.json`, else `brain/`, else the only brain); the address is kept up to date (`history.replaceState`), which makes it possible to keep one tab per brain. On a change, the page resets what belongs to the previous brain (project filter, group, collapsed groups, selection, detail panel, open document, Git selection and detail, tools output, **Undo** stack) then reloads the views with the usual refresh functions; the text typed in the search fields and the Owner and Status filters remain. The change is refused while a write or a tool is running, and an action or a note that has been modified and not saved asks for confirmation. A read response that arrives after the change is ignored.

On the server side, `--brain` only designates the default brain (without the option: `Work/brain`) and `WORK_DIR` another Work root. If it is not among the discovered brains, it is offered anyway, alone or at the head of the list. Each brain has its own `Store`, created on the first request and kept: its undo stack and its document cache are not mixed with those of the others. All `/api/…` routes accept an optional `brain=<name>` parameter; when absent, it is the default brain and the responses are those of before. The name must be exactly that of a brain discovered at the time of the request: a path, an unknown, empty or repeated name gives a 400 error (`{"error": "Unknown brain."}`), and a brain with no `projects/` folder a 404. The tool launched from **Tools** receives the chosen brain (`BRAIN_DIR`, and `--brain <folder name>` for **Brain map**, whose script chooses a brain by name and would otherwise print them all), the **Git** view shows Work and the folder of the chosen brain, and writes (actions, notes, history, deletion, undo) reach only it. Route: `GET /api/brains` → `{"brains": [{"name", "label", "scope", "description", "default"}], "default": "<name>"}` (`label`: the short name shown, `Perso` for `brain-perso`; `scope` and `description` are `""` without `brain.json`; the list is re-read on every call; no token and no write).

## Notes and Search

**Notes** lists the brain's notes (those of `GET /api/notes`: `<project>/notes/*.md` and the Inbox), the most recent first, with the project, the date and an excerpt; **Search** searches all the brain's Markdown documents. Both views share the reader on the right (below the list on a narrow screen) and the filters: the sidebar project (a client keeps the documents of all its missions) and the **Location** chip (**Inbox** for the `inbox/` folder, **Outside projects** for documents that are under no project folder; choosing one removes the sidebar project, and the other way round).

Search scope: all `*.md` files under the brain, except any path with a component that starts with `.` (`.git`, `.data`, `.vscode`, `.obsidian`, `.trash`…), symbolic links, anything outside the brain and files larger than 1 MB. The parsed catalog is cached per file (path, modification date, size): only modified files are re-read.

In **Search**, the header field (focused when entering the view, run after 200 ms of inactivity or immediately with Enter) replaces the **Recently modified** document list with the results: title (first `# ` heading, otherwise the file name) with the terms highlighted, project, shortened path (without `projects/` or `clients/`) and up to 2 excerpts of about 160 characters; the number of results is shown in the header. Search rules: accents, case and multiple spaces are ignored (`réunion` finds `REUNION`); words separated by spaces must all appear (AND) in the title, the path or the content; `"between quotes"` searches an exact phrase; 10 terms at most, 60 characters per term and 300 characters in total (beyond that, a 400 error), single-character terms are ignored. The ranking weights the title (×10), the path (×5), Markdown heading lines (×3) and the occurrences in the body (capped), with a slight advantage to recent files; the 50 best results are returned (with a client chosen in the sidebar, the filtering applies to these 50).

Reader: the document is rendered to HTML by the server (`markdown-it-py`, CommonMark with tables and strikethrough), in lines of at most 72 characters. Raw HTML in documents is never interpreted: it is displayed as text, except a bare `<u>…</u>` (no attribute, no other tag), which is underlined, as in Obsidian. Images are not loaded (their alt text is shown). Headings receive an identifier (prefix `h-`) for anchors. Relative links to another `.md` of the brain open that document in the same reader, with a **Back** button; `http(s)` and `mailto` links open in a new tab (`noopener noreferrer`); other links (non-Markdown files, documents outside the brain or missing, `javascript:`, `data:`, `file:` schemes…) are displayed as text with the tooltip "File not shown here". A document opened from a search has its terms highlighted (500 highlights at most) and scrolls to the first one. For a project or Inbox note, **Edit** opens the raw Markdown; **Save** (or ⌘ Enter) replaces the file if its version has not changed on disk (otherwise a conflict message), **Cancel** abandons, with a confirmation if unsaved changes remain, and the rendering is refreshed after saving. Other documents are read-only.

**Markdown toolbar.** The content field of **New note** and the note editor (not the one-line notes of an action) share a formatting toolbar: bold, italic, underline (`<u>…</u>`, which Obsidian renders), strikethrough, bulleted and numbered lists, checklist, quote, inline code, link and arrow. A button wraps the selection, or the caret, in its markers and pressing it again unwraps; the line formats act on every selected line and toggle off when all of them have it (a numbered list renumbers and continues the list above). The link button leaves the `url` selected; a long press, a right click or ↓ on the arrow button offers `←`, `⇒` and `↔`. Edits use the browser's typing command, so undo and redo keep working. While the text has the focus: ⌘ B, I, U, K and ⇧ ⌘ X (Ctrl on Windows and Linux). The bar is a `toolbar` (one Tab stop, then the arrow keys) that wraps on a narrow screen; the text edits live in `static/md-edit.js`, which the tests also run under node.

**New note** asks for a title, a project (by default the project chosen in the sidebar, otherwise **Inbox (to triage)**) and a content; after the creation, the page switches to the **Notes** view and shows the note. A project is a folder that contains `state/actions.md`; the note lives in `<project>/notes/YYYY-MM-DD-<slug>.md`, a flat file whose `notes/` folder is created if needed. The **Inbox (to triage)** target, offered first, writes to `inbox/YYYY-MM-DD-<slug>.md` at the root of the brain (folder created if needed), for raw notes that an agent will triage later; its header has no project link: `> Note from DD/MM/YYYY · to triage`. Inbox notes appear with the project "Inbox" and can be edited like project notes (the folder's `README.md` and the capture scratchpad `inbox/inbox.md` are never listed or editable as notes). The file never replaces an existing file (suffix `-2`, `-3`… on a collision) and starts with `# Title`, a line `> Note from DD/MM/YYYY · project: [label](relative link)` to the project page (failing that, to its register, and the label then ends with `(register)`), and the content. The slug is lowercase ASCII, 60 characters at most; the title is 1 to 150 characters on one line, the content 100 KB at most. Writes are protected like those for actions (host, origin, token, JSON, write lock) and go through the same undo stack: undoing a creation deletes the note (and the `notes/` or `inbox/` folder if this write created it and it remains empty), undoing an edit restores the exact bytes; the undo is refused if the file has changed in the meantime. After an undo, the views re-read the list or run the search again and redisplay the document ("This document no longer exists." if it has gone). Routes: `GET /api/search?q=&project=` (`project`: path of a register, `inbox`, `none` or empty; response `query`, `terms`, `results` [`id`, `title`, `project`, `register`, `snippets` [`text`, `ranges`], `score`], `total`, `truncated`), `GET /api/docs/recent?project=`, `GET /api/docs/render?id=` (`id` exactly equal to a catalog identifier, otherwise 404; response `id`, `title`, `project`, `register`, `html`, `note`, `version`), `GET /api/notes`, `GET /api/notes/content?id=`, `POST /api/notes` (`title`, `register`, `content`; `register` is required: path of a project register, or `inbox` for the Inbox), `PATCH /api/notes` (`id`, `version`, `content`; 409 if the version is stale).

## Tools

The **Tools** view lists, by collapsible group (Memory, Actions, Repositories), the existing commands (reads, previews and confirmed writes): checks of the brain and of links (**Check links**, **List brains**, **New transcripts**), and two read-only reports on the chosen brain: **Brain map** (`brain/brain-state.py map`, one line per project: page, register prefix, actions by state, overdue, proposed decisions, last timeline entry) and **Timeline months to move** (`brain/timeline.py roll`, a dry run: the timeline entries of past months that would move to `journal/`; its `--write` form is not offered), the repositories check (**Check repositories**), and the tools of the **Actions** group: **Text view of actions**, **Actions to sort (preview)** and **Sort actions by status** (`brain/action.py sweep`, with `--write` for the second; it files each action under the section that matches its status), **Actions to archive (preview)** (`brain/action.py`, changes nothing) and **Archive actions** (`brain/action.py --write`), which moves the actions closed for more than 30 days to `state/actions-archive-YYYY.md`. Each row gives the name, a one-line description (complete in the tooltip with the command) and **Run**. A tool that writes brain files carries the mark "writes to the brain", asks for a confirmation before running and refreshes the lists afterwards; its writes do not go through the interface's undo stack (recover them with Git). The output is displayed in a panel under the list, with the command that was run, without being saved by the interface. The allowed commands and their arguments are fixed on the server; no field makes it possible to run a free command. Cloning repositories stays in its dedicated workflow.

If **New transcripts** shows "Access denied", its input folder configured in the brain is not readable by the process that launches Actions Brain. Check the macOS permissions and the availability of OneDrive, then run the command again; the tool does not present an incomplete list as if it were exhaustive.

## Git

The **Git** view displays, read-only, the local changes of the two repositories Work and brain (the folder of the chosen brain), one under the other on the left: branch, ahead/behind (`↑` `↓`) relative to the last local sync of the remote branch, staged, modified and untracked files with their `+N −M` counters, and the 2 latest commits (those not yet pushed are marked "unpushed"). A click on a file or a commit shows its diff on the right (below on a narrow screen); **Refresh** also re-reads this view. The server only runs read-only Git commands with fixed arguments (`status`, `diff`, `log`, `show`, `rev-list`), without a shell, with a 10-second timeout, without `GIT_TERMINAL_PROMPT` or optional lock, and never contacts the network (no `fetch`, `pull`, `push` or `ls-remote`: the behind count shown is therefore exact only after a sync done elsewhere). The requested path must appear in the current Git state and the commit among the 2 listed, otherwise the response is 404; a file that is both staged and modified appears in both groups, and for a file that is only staged the staged diff is served. Outputs are truncated at 300 KB. Sensitive files (`.env*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `id_ed25519*`, `*.kdbx`, `credentials*`, `*secret*`, `*.token`) are listed but their content is never displayed, neither in the diff nor in the detail of a commit. No commit, staging or push action is possible from the interface. Routes: `GET /api/git`, `GET /api/git/diff?repo=&path=&staged=0|1`, `GET /api/git/commit?repo=&hash=`.

## Data and security

The `projects/**/state/actions.md` files of the chosen brain are the only source of truth. The browser reads their state on opening and with **Refresh**; it stores no copy of the tasks. Writes go through a server bound to `127.0.0.1`, with a check of the origin and of the line's version to report concurrent modifications. No data is sent to a host or an external service. IDs are assigned from the existing prefix and the highest number of the project; a register with no established prefix must first be configured according to the brain's conventions.

The `tasks.md` page of a brain provides the same views in Obsidian, thanks to the Tasks, Meta Bind and Templater plugins (settings to make once per machine: `kit/obsidian/README.md`). Both interfaces use the same registers; no additional synchronization is needed.
