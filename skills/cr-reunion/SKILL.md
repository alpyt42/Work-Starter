# cr-reunion

Destination: the work brain `brain/` by default. When the user says a meeting is personal (career, interview, personal project), write to `brain-perso/` instead: read `brain-perso/AGENTS.md`, use `brain-perso/.data/transcripts.json` as the processing state and `brain-perso/projects/<project>/sources/YYYY-MM/` for the minutes, and run the link check with `BRAIN_DIR=brain-perso`. Never mix the two: nothing personal in `brain/`, nothing client-related in `brain-perso/`. A personal transcript is only recorded in `brain/.data/transcripts.json` as `destine-brain-perso`, with no detail.

Read the transcript source directory from `brain/.data/local-paths.json` (described in `brain/docs/LOCAL-WORKFLOWS.md`) or ask the user for its location; never hard-code a machine path in this repository. The processing state is `brain/.data/transcripts.json`. Never move or delete source transcripts or open audio unless the user requests it. Read `brain/AGENTS.md` before editing memory.

1. List new transcript text files and compare them with the processing state. Use the quick commands in `brain/docs/LOCAL-WORKFLOWS.md` to list unprocessed transcripts in one call; if the configured folder is missing, ask the user before searching elsewhere. Treat automatic summary files as hints, never source material. Group recordings with the same meeting identifier; retain the most complete transcript and mark the rest as duplicates.
2. For each candidate, show its date, approximate length, detected speakers, and a short identifying excerpt. An available calendar may suggest a meeting within 30 minutes of the recording, but the user confirms the client or internal project, mission, title, and any split into multiple meetings. Ask about no more than four recordings at a time. Do not draft the minutes before this confirmation.
3. Read the client index, mission page, action and decision registers, relevant workstream, recent source index, and participant pages. Use this context to recognize names and existing actions, never to add facts absent from the transcript.
4. Read the complete transcript. Write one dated Markdown source under `brain/projects/clients/<client>/missions/<mission>/sources/YYYY-MM/`, or the matching internal or personal project. Include source, participants, summary, subjects, proposed decisions, actions, changes since the last meeting, and points to verify. Link it from the monthly index. Use a unique suffix if the same date and title already exist. Keep the transcript and audio at their original location, and describe their provenance in words (tool, recorder, date) without citing their local path or file name; the same applies to any document outside `Work/` used as a hint. A OneDrive or SharePoint web link may stay for traceability.
5. Use memory to resolve names and action IDs, never to add facts absent from the transcript; label context from memory separately. Do not copy secrets, private health or career information, or confidential side conversations into the minutes. Mark uncertain speakers and unclear passages rather than guessing. Do not attribute a decision or action to a speaker when diarization is unreliable.
6. Reconcile the mission page, action and decision registers, kanban, and today view in one pass. Search all missions of a client before allocating an action ID. A decision mentioned in a meeting remains proposed until the user confirms it. Update the processing state for every processed, duplicate, ignored, or excluded recording only after the destination files exist.
7. Run `uv run tools/check-links.py`, inspect the diff, and report files changed and open questions. Propose a commit; perform commit and push only on separate explicit requests.
